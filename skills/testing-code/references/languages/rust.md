# Rust testing mechanics

How to write the tests the [runbooks](../runbooks/unit.md) describe, in Rust with cargo test, cargo-nextest, rstest, mockall and proptest. Standards are in [testing-principles](../../../testing-principles/SKILL.md); the shape of a test body is the [test body template](../test-body-template.md). The thirteen sections match the [Python page](python.md) in order, but this page is shorter: it spends its words where Rust differs, including the ownership rules that trip up test doubles.

```toml
[dev-dependencies]
mockall = "0.15"
rstest = "0.28"
proptest = "1.12"
tempfile = "3.27"
tokio = { version = "1.54", features = ["rt", "rt-multi-thread", "macros", "time", "test-util"] }
```

`rt-multi-thread` is only for `#[tokio::test(flavor = "multi_thread")]`; without it that flavor does not compile. Drop it if every async test uses the default runtime.

Run the suite with `cargo test`, or with `cargo nextest run` once you install it (`cargo install cargo-nextest --locked`). `cargo test` runs the tests of one binary as threads in one process. nextest runs each test in its own process, which its docs give as a deliberate, permanent design choice. Two things follow. A test that leaks global state or aborts cannot hurt its neighbors, and killing one test (for a timeout) is safe. And any state you hoped to share between tests through a `static` is not shared under nextest, so a suite that passes only under `cargo test` was depending on that sharing ([shared mutable state](../code-smells.md#shared-mutable-state)).

## Layout and naming

```text
Cargo.toml
src/lib.rs
src/orders.rs
tests/checkout.rs
tests/common/mod.rs
```

- **Unit tests** live in the same file as the code, in a `#[cfg(test)] mod tests` that begins with `use super::*;`. Being a child module, they can reach private items, which is the one place Rust lets a test see a private function. Prefer testing through the public function anyway ([testing private internals](../code-smells.md#testing-private-internals)).
- **Integration tests** are files in `tests/`. Each file is compiled as its own crate and sees only the public API, which makes them a natural fit for the integration kind. Shared helpers go in `tests/common/mod.rs` (a `mod.rs` file is not compiled as its own test crate), and each test file declares `mod common;`.
- Name each test for the behavior: `sends_one_receipt_after_a_successful_charge`, not `test_1`. The name is what appears in the failure line.
- Mocks generated by `#[cfg_attr(test, mockall::automock)]` exist only under `cfg(test)`. They are therefore not visible to the files in `tests/`, because the library is compiled without `cfg(test)` for them. For an integration test either write a small hand-made fake or put the mock behind a feature your dev-dependencies turn on.

## Fixtures, setup, teardown

Rust has no `setUp` or `tearDown`. A value is built in the test (or by a helper) and cleaned up when it is dropped, at the end of its scope, even if the test panics. That makes `Drop` the teardown: `tempfile::TempDir` removes its directory when it goes out of scope, and a mock checks its expectations when it is dropped.

rstest adds Python-style fixtures: a `#[fixture]` function, requested by naming it as an argument.

```rust
use rstest::{fixture, rstest};

#[fixture]
fn gateway_mock() -> MockPaymentGateway {
    MockPaymentGateway::new()
}

#[rstest]
fn declines_when_the_charge_fails(mut gateway_mock: MockPaymentGateway) {
    gateway_mock.expect_refund().never();
    // ...
}
```

- Each test gets a fresh value from the fixture, which is the default you want (P13). `#[once]` shares one value across tests; it hands out a reference, so use it only for read-only state.
- Fixtures can take other fixtures as arguments. Keep expected values as `const` items at the top of the `tests` module so the fixture and the assert share one name ([values defined far from the test](../code-smells.md#values-defined-far-from-the-test)).
- `mut` is needed on a mock argument because setting expectations takes `&mut self`.
- For a temporary directory, hold the `TempDir` for the whole test: `let dir = tempfile::tempdir()?;`. Calling `.path()` on a temporary that is dropped at the end of the statement leaves you a path to a deleted directory.

The [fixtures runbook](../runbooks/fixtures.md) has the steps for deciding what a fixture should build.

## Doubles: stub, mock, autospec equivalent, fake

Choose the double by what the test asserts (see [doubles](../../../testing-principles/references/doubles.md)). A stub supplies data, a mock is an object the test asserts calls on, a fake is a small working replacement.

### Stub

A stub is a value of the real type. Rust has no way to hand the compiler a half-built struct, so a "stub" is the real struct with the fields the test cares about and plain values for the rest:

```rust
let charge = Charge { id: "ch_123".into(), succeeded: true };
```

If constructing the real struct is noisy, add a test-only constructor or a `Default` impl rather than a mock.

### Mock and the autospec equivalent: mockall

The trait is the spec. `#[automock]` generates a `Mock<Trait>` struct from the trait's real signatures, so an expectation for a method that does not exist, or with the wrong argument types, does not compile. That is Rust's autospec, and it works without runtime introspection.

```rust
#[cfg_attr(test, mockall::automock)]
pub trait PaymentGateway {
    fn charge(&self, token: &str, cents: u64) -> Charge;
    fn refund(&self, charge_id: &str);
}
```

Write the code under test against the trait, taking `&impl PaymentGateway` or `&dyn PaymentGateway`, so a test can pass the mock.

The exact-call rule (P10) maps onto mockall like this:

```rust
use mockall::{predicate::eq, Sequence};

#[rstest]
fn sends_one_receipt_after_a_successful_charge(
    mut gateway_mock: MockPaymentGateway,
    mut mailer_mock: MockMailer,
) {
    let charge = Charge { id: "ch_123".into(), succeeded: true };
    let mut order = Sequence::new();
    gateway_mock
        .expect_charge()
        .with(eq(TOKEN), eq(TOTAL_CENTS))
        .times(1)
        .in_sequence(&mut order)
        .return_const(charge);
    mailer_mock
        .expect_send_receipt()
        .with(eq(EMAIL), eq("ch_123"))
        .times(1)
        .in_sequence(&mut order)
        .return_const(());
    gateway_mock.expect_refund().never();

    let result = place_order(&gateway_mock, &mailer_mock, EMAIL, TOKEN, TOTAL_CENTS);

    assert_eq!(result, Outcome::Confirmed { charge_id: "ch_123".into() });
    gateway_mock.checkpoint();
    mailer_mock.checkpoint();
}
```

- `.with(eq(..))` pins the arguments of that expectation. `.times(1)` pins how often it is called; `.times(n)` or a range also work. Without `.times`, an expectation allows any number of calls, which is the gap P10 warns about, so always write it.
- A call that matches no expectation panics, so an extra or wrong call fails the test at once. That covers the "no other calls" half of the rule. A missing call is caught when the mock is dropped, or earlier by `checkpoint()`. Both were confirmed with `#[should_panic]` tests while writing this page.
- `.never()` is the not-called assert. A method with no expectation at all also panics if called, so `.never()` is for stating the intent.
- Order is part of the assertion by default (P10), so pin it with `Sequence`. One `Sequence` can span several mocks, as in the example (charge before receipt), and several expectations on one mock (two receipts in the order the code sends them):

```rust
let mut order = Sequence::new();
mailer_mock
    .expect_send_receipt()
    .with(eq("ada@example.com"), eq("ch_123"))
    .times(1)
    .in_sequence(&mut order)
    .return_const(());
mailer_mock
    .expect_send_receipt()
    .with(eq("bo@example.com"), eq("ch_123"))
    .times(1)
    .in_sequence(&mut order)
    .return_const(());
```

Calls made in the other order panic. Leave the `Sequence` out only when the order has no effect on the outcome, and say so once in the test, for example in a one-line comment.
- `checkpoint()` validates every expectation now and clears them, so you can set new ones mid-test. Call it at the end when you want the failure to point at the test body instead of at the drop.
- For an argument you cannot compare with `eq`, `withf(|x| ...)` takes a closure. mockall's docs say a method with a lifetime parameter, or a concretized generic method, cannot be matched with `with` and needs `withf`.
- Return values: `return_const(value)` clones the value on each call, and `returning(|args| ...)` computes a fresh one per call. For a value that cannot be cloned and is returned once, use `return_once(move |args| value)`.

Ownership and lifetimes, for the places a double trips:

- **Setting expectations borrows the mock mutably; passing it to the code borrows it immutably.** That is why the mock is `mut` and why every `expect_*` call comes before `place_order(&gateway_mock, ...)`. You cannot add an expectation while the code holds a shared reference to the mock, so finish the setup and then lend it. That is safe advice rather than a hard rule: with non-lexical lifetimes, a shared borrow only has to end before the next `expect_*` call.
- **Moving a mock gives it away.** `consume(Box::new(mailer))` moves `mailer` into the box, so calling `mailer.checkpoint()` afterwards is a compile error ("borrow of moved value"). The mock is still verified when `consume` drops it. If you need to inspect it after, pass a reference instead of moving it.
- **Mocks and references.** A mocked method that returns a reference works only when that reference lives as long as the mock or is `'static`, per the mockall docs. If a trait method returns a borrowed value tied to its arguments, return an owned value (`String`, `Vec`) in the trait instead, or test through a fake.
- **Mocked traits are checked at compile time, so many failures are compile errors.** If the mock won't build for a generic or lifetime-heavy trait, a hand-written fake (a plain struct implementing the trait with a `Vec` of recorded calls) is often shorter than fighting `automock`.
- **Static methods are global.** Mocking an associated function with no `self` makes expectations global to the process, so tests that use it interfere under `cargo test`'s threads. Under nextest each test is its own process and they do not. Prefer to inject the dependency instead.

mockall has no built-in matcher that compares a mock's whole call list, so the chain of `.times()`, `.with()` and `Sequence` is the way to state the exact calls.

### Fake

A fake is a small working stand-in: a struct implementing the trait over a `HashMap` or a `Vec`, usually written by hand.

```rust
#[derive(Default)]
struct InMemoryOrders {
    rows: std::cell::RefCell<std::collections::HashMap<String, Order>>,
}

impl Orders for InMemoryOrders {
    fn save(&self, id: &str, order: Order) {
        self.rows.borrow_mut().insert(id.to_string(), order);
    }
}
```

Here `Orders` is the trait the code under test depends on, and `save` takes `&self`. Use a fake when the test cares about the outcome, not the calls ([change-detector tests](../code-smells.md#change-detector-tests)). `RefCell` lets a trait method that takes `&self` still mutate the map; it moves the borrow check from compile time to runtime. If the fake must be shared between threads, use `Mutex` instead.

## Parametrization

rstest's `#[case]` runs one body over several rows and names each case, so a failure says which one. It replaces a loop in a test (P3, [logic in tests](../code-smells.md#logic-in-tests)).

```rust
#[rstest]
#[case::zero(0, "$0.00")]
#[case::under_a_dollar(5, "$0.05")]
#[case::thousands(123456, "$1,234.56")]
fn formats_price(#[case] cents: u64, #[case] expected: &str) {
    assert_eq!(format_price(cents), expected);
}
```

- `#[case::name(...)]` makes the generated test `formats_price::case_1_zero`. Always name the cases.
- `#[values(...)]` on an argument runs the cartesian product of the lists. Keep them short; the count multiplies.
- Write the expected value as a literal in each row.
- For a pure function over arbitrary inputs, a property test (below) says more than a long table.

## Determinism: time, randomness, network, ordering

### Time

Inject a clock (a `Fn() -> SystemTime` or a trait) when you can. For tokio code, pause the runtime clock:

```rust
#[tokio::test(start_paused = true)]
async fn waits_without_real_time() {
    let started = tokio::time::Instant::now();

    let result = wait_then_flag(Duration::from_secs(3600)).await;

    assert_eq!(result, "done");
    assert!(started.elapsed() >= Duration::from_secs(3600));
}
```

`start_paused = true` needs tokio's `test-util` feature and works only on the default `current_thread` flavor: `#[tokio::test(flavor = "multi_thread", start_paused = true)]` fails to compile with "The `start_paused` option requires the `current_thread` runtime flavor". With the clock paused, tokio advances it by itself whenever the runtime has nothing to do, so a one-hour sleep finishes at once. The same is available inside a test as `tokio::time::pause()` and `tokio::time::advance(duration)`. Use `tokio::time::Instant` for measuring; `std::time::Instant` is not paused. The example above ran here.

### Randomness

Inject the generator or take a seed as a parameter. proptest prints a failing input and records it, so a failure replays.

### Network

Rust has no global network interceptor like MSW. Two options:

1. **Put the HTTP client behind a trait** and use a mock or fake in unit tests. The network is never touched.
2. **Run an in-process server** (wiremock or httpmock; only their versions were checked) on a random local port for the integration kind, and point the client at it.

Either way, a unit test that reaches the real internet is a bug in the test.

### Ordering

`cargo test` runs tests in parallel threads in an order you do not control; nextest runs them in parallel processes. Pin neither. A test that needs another test to have run first is broken ([shared mutable state](../code-smells.md#shared-mutable-state)). To expose hidden order dependence, run a pass with `cargo test -- --test-threads=1` and one with the default; to catch hidden sharing, run nextest, where it cannot exist.

## Isolation and cleanup

- Own your state. Create it in the test, let `Drop` clean it. A `TempDir` removes itself, so a test never writes into the repository.
- Process-global state (environment variables, the current directory, a `static`, a logger) is shared by threads under `cargo test`. `std::env::set_var` is `unsafe` in the 2024 edition for exactly this reason. Pass values in as parameters instead.
- nextest isolates each test in a process, which removes most global-state leaks. Rely on it in CI, but do not rely on it to hide a design that needs global state.
- `serial_test` (`#[serial]`) forces named tests to run one at a time. Use it only as a last resort for a resource you cannot make per-test, such as a fixed port a library insists on; it hides the coupling and slows the suite.
- `#[should_panic(expected = "text")]` passes when the body panics with that text. The message check matters: a bare `#[should_panic]` passes on any panic, including a typo that panics for the wrong reason. Prefer a test returning `Result` or asserting on the returned error where you can.

## Async

- Use `#[tokio::test]` for async tests. It builds a runtime per test. The default is a single-threaded runtime; ask for `flavor = "multi_thread"` only when the code needs it, and enable tokio's `rt-multi-thread` feature for it.
- Wait on a condition, not on time. Use a channel, `tokio::sync::Notify`, or `tokio::time::timeout(Duration::from_secs(5), future)` so a hang becomes a failure instead of a stuck job ([bare sleeps](../code-smells.md#bare-sleeps)). With paused time, `timeout` costs no real seconds.
- rstest supports `async` fixtures and tests, and a `#[timeout(...)]` attribute on async tests (the `async-timeout` feature is on by default).
- Await spawned tasks (`handle.await`) before asserting. A test that spawns work and returns first passes before the work runs.
- When the test function returns, its runtime shuts down and any task still pending is dropped. An assertion inside a spawned task that has not finished never runs.

## Performance

Measure first ([slow tests runbook](../slow-tests.md)). The Rust levers:

- `cargo nextest run` is usually the first thing to try on a large suite; it schedules tests across processes (`-j` sets the count).
- Split work across CI machines with nextest's `--partition`.
- Build time often dominates. Share one `target/` across jobs through your CI cache. Many small files in `tests/` each link a separate binary, so group related integration tests into fewer files.
- Pause time instead of sleeping (above). Do not shorten a timeout to make a slow test pass; the test would then be flaky instead.
- Keep property-test case counts moderate in the default run; `PROPTEST_CASES` raises it for a nightly job.
- Run `cargo test` on a single test while iterating (`cargo test sends_one_receipt`); run the whole suite before you push.

## Coverage, mutation and property-based tools

**Coverage: cargo-llvm-cov** (0.9.1). Install it, then `cargo llvm-cov` for a text summary, `cargo llvm-cov --html` for a report, or `cargo llvm-cov nextest` to use nextest as the runner. `--fail-under-lines <MIN>` fails the run below a line threshold. Its README marks branch coverage and doctest coverage as unstable, so rely on line and region coverage. This page did not run it. Coverage shows what the suite never executed, not whether the executed code is checked.

**Mutation: cargo-mutants** (27.1.0, from crates.io; the README describes it as working on trees whose tests run under `cargo test` or `cargo nextest run`). It changes the code, reruns the tests, and reports mutants no test caught.

```sh
cargo install --locked cargo-mutants
cargo mutants -f src/orders.rs
cargo mutants --in-diff changes.diff
```

`-f` limits mutation to one file; `--in-diff` tests only the mutants overlapping a diff (generate it with `git diff`), which is how you make it affordable on a pull request. It needs non-flaky tests, so fix or quarantine flakes first. A surviving mutant is a missing or weak assertion. The [mutation testing runbook](../runbooks/mutation-testing.md) has the procedure. This page did not run it.

**Property-based: proptest** (1.12.0). State a property and let proptest search for a counterexample, then shrink it.

```rust
use proptest::prelude::*;

proptest! {
    #[test]
    fn price_always_has_two_decimals(cents in 0u64..10_000_000_000) {
        let text = format_price(cents);
        prop_assert!(text
            .rsplit_once('.')
            .is_some_and(|(_, decimals)| decimals.len() == 2));
    }
}
```

Use `prop_assert!` and `prop_assert_eq!` inside `proptest!`. A failing case is saved to a file under a `proptest-regressions/` directory at the crate root (next to `src/`, mirroring the source path with a `.txt` extension, per the proptest docs for the default persistence) and replayed first on later runs; commit that directory. `PROPTEST_CASES` overrides the number of cases. The [property-based runbook](../runbooks/property-based.md) covers choosing properties.

## Integration and data: factories, databases, rollbacks

Build test data with a function that takes the one value the test cares about and defaults the rest ([values defined far from the test](../code-smells.md#values-defined-far-from-the-test)). A struct update with `..Default::default()` is the idiomatic factory:

```rust
fn user(overrides: impl FnOnce(&mut User)) -> User {
    let mut user = User { email: "ada@example.com".into(), is_member: false, ..User::default() };
    overrides(&mut user);
    user
}
```

For databases:

- **Rollback per test**: open a transaction at the start of the test, run the code against it, and drop it without committing. In sqlx a transaction that is dropped uncommitted rolls back. This was not run for this page, so confirm it for your driver. It works only when the code under test uses the connection or transaction you pass in.
- **Truncate or recreate** when the code opens its own connections. A throwaway database per test (created from a template, dropped at the end) is slower but isolates fully; nextest's process-per-test makes the cleanup easy to keep per test.
- Run migrations once per test run, against a throwaway database, then rely on rollback or truncate per test.
- Mark expensive database tests `#[ignore = "needs database"]` only if the default run must stay fast, and run them in their own job with `cargo test -- --ignored` or, under nextest, `cargo nextest run --run-ignored only`. The ignore reason does not select anything: `cargo test -- --ignored` runs every ignored test, database and quarantined alike. Put database tests in a `database` module and quarantined tests in a `quarantine` module, then select by name (`cargo test -- --ignored database`, run on cargo 1.99.1 on 2026-11-13).

The [integration runbook](../runbooks/integration.md) has the steps.

## Anti-patterns

The shared list is in [code smells](../code-smells.md). The ones that show up most in Rust suites:

- A mock expectation with no `.times()`, so any number of calls pass ([tests that cannot fail](../code-smells.md#tests-that-cannot-fail)).
- `.returning(|_| ...)` closures with logic inside, which grow into a second implementation ([logic in tests](../code-smells.md#logic-in-tests)).
- Expectations with no `Sequence` where the order of calls is part of the outcome, so a swapped pair passes. Where the order has no effect, leaving it out is fine if the test says so once.
- Mocking every collaborator so the test restates the implementation ([change-detector tests](../code-smells.md#change-detector-tests)).
- Twenty lines of expectation setup for a three-line function ([over-specified or over-mocked setup](../code-smells.md#over-specified-or-over-mocked-setup)). Write a small fake instead.
- `std::thread::sleep` or `tokio::time::sleep` in a test to wait for work ([bare sleeps](../code-smells.md#bare-sleeps)).
- `unwrap()` chains everywhere. A test that returns `Result<(), E>` and uses `?` stops at the first error with its message, and reads shorter.
- `#[should_panic]` with no `expected = "..."`.
- Tests that share a `static`, a fixed file path or a fixed port ([shared mutable state](../code-smells.md#shared-mutable-state)).
- Testing private helpers through the `tests` module instead of through the public function ([testing private internals](../code-smells.md#testing-private-internals)).
- Several acts and asserts in one test ([one test covering several behaviors](../code-smells.md#one-test-covering-several-behaviors)).
- Many unrelated `assert!` lines with no message ([assertion roulette](../code-smells.md#assertion-roulette)). Compare one expected value with `assert_eq!`.
- An `#[ignore]` with no reason, owner or date.

### Quarantining a flaky test

The [quarantine runbook](../flakes/quarantine.md) decides whether to quarantine and which mechanism to use. Rust has no expected-fail marker for a flaky test: `#[should_panic]` inverts the result and breaks the run when the test passes, so it fits a test that fails on every run, not one that fails sometimes. The syntax for the mechanism Rust does have, an ignore that a separate job still runs:

```rust
#[test]
#[ignore = "flaky: depends on worker startup order, tracked in ORDERS-412, owner ada, review 2026-12-01"]
fn worker_publishes_event() {
    // body unchanged
}
```

- The gating run (`cargo test` or `cargo nextest run`) skips it. The reason shows in `cargo test` output.
- The non-gating job runs only the ignored tests: `cargo nextest run --run-ignored only` or `cargo test -- --ignored`. Both executed the ignored test (cargo 1.99.1, 2026-11-13); the job exits non-zero when it fails, so mark it non-blocking in CI (`continue-on-error` in GitHub Actions) and watch its results.
- `--run-ignored all` (nextest) or `--include-ignored` (cargo test) runs everything together, for a full local run.
- That arrangement is the runbook's "separate non-gating run": the test keeps running and reporting, just not in the gate.
- Put the owner, the date and the tracking link in the reason string so a search finds them.
- Select quarantined tests by name, not by reason: keep them in a `quarantine` module and run `cargo test -- --ignored quarantine` (checked on cargo 1.99.1, 2026-11-13), where `--ignored` alone also runs every other ignored test. Under nextest the same split is a filterset such as `-E 'test(~quarantine)'` (not run for this page).
- nextest's `--retries <N>` reruns a failing test. It hides a flake rather than quarantining it, so the runbook's tracking still applies.
